# Meeting-note Feature — Changes, Testing, and Next Steps

Date: 2026-07-23

This document summarizes the recent changes made to add a `meeting note` workflow to the Obsidian notes pipeline, the rationale, how to test the changes locally, and recommended next steps.

## Summary

- Added a new intent trigger: "meeting note". When spoken at the start of a recording the system will create a meeting-style note in the Obsidian inbox rather than a daily-note bullet.
- The transcription pipeline will prefer a `whisperx`-based path when available and fall back to the existing `faster-whisper` model when not.

## Files changed

- `config.py`: added `MEETING_NOTE_TRIGGER_PHRASE = "meeting note"` to centralize the trigger phrase.
- `intent.py`: extended `detect_intent()` and `strip_intent_trigger()` to recognize and strip the `meeting note` trigger.
- `main.py`: routed `meeting_note` to a new `create_meeting_note()` writer (keeps the existing summarization/title generation logic).
- `obsidian_writer.py`: added `create_meeting_note(title, content, timestamp)` which reuses the inbox filename convention (`YYYY-MM-DD Title.md`).
- `transcribe.py`: added `_transcribe_with_whisperx()` and updated `transcribe()` to attempt `whisperx` first and fall back to `faster-whisper`.
- `test_quick_note.py`: added a regression test asserting the `meeting_note` trigger is detected and the trigger text is stripped correctly, while preserving the existing quick-note filename test.

## Behavior details

- Intent detection now checks leading filler words (config.FILLER_WORDS) then matches `task`, `quick_note`, `meeting_note`, or falls back to `note`.
- For `quick_note` and `meeting_note`, the transcript text has the trigger phrase removed before title generation and summarization.
- `transcribe()` will raise if both transcription paths fail; if `whisperx` is not installed or fails, `faster-whisper` remains the default reliable fallback.

## Dependencies

System requirements:

- `ffmpeg` must be installed and available on `PATH` for metadata probing and some decoding paths.

Python packages (project already includes some; add/verify as needed):

- `faster-whisper`
- `openai`
- `python-dotenv`
- `mutagen`
- `watchdog`
- Optional (for diarization / speaker-aware transcription):
  - `whisperx`
  - `torch` (matching your system/CPU or CUDA capabilities)
  - `pyannote-audio` (if you plan to use speaker diarization pipelines)

If you plan to enable the diarization path, pin `torch` and `whisperx` versions compatible with your platform (CPU vs CUDA). The repo does not force-install these optional packages—`transcribe.py` uses a try/except and falls back gracefully.

## How to test locally

1. Activate the project's virtual environment (Windows PowerShell):

```powershell
(Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned)
& .\venv\Scripts\Activate.ps1
```

2. Run unit tests (already executed during development):

```powershell
.\venv\Scripts\python.exe -m unittest -v
```

3. Quick intent check (Python REPL or one-liner):

```powershell
.\venv\Scripts\python.exe -c "from intent import detect_intent, strip_intent_trigger; print(detect_intent('meeting note follow up from the planning call')); print(strip_intent_trigger('meeting note follow up from the planning call'))"
```

4. End-to-end sample (replace SAMPLE.wav with a real audio file path):

```python
from main import process_file
process_file(r'C:\path\to\SAMPLE.wav')
```

This will attempt transcription (whisperx then faster-whisper), generate a title/summary via the OpenAI client, and write a note into the configured Obsidian inbox/daily note locations.

## Next steps and recommendations

- Consider adding a `--dry-run` or `--verbose` flag to the processing pipeline for troubleshooting transcription and OpenAI calls during development.
